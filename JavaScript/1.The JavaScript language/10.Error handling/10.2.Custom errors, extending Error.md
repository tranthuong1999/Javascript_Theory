1. Extending Error
1.1. Tại sao cần Custom Errors?
Vấn đề:
Trong JS , chúng ta đã biết các lỗi có sẵn như :
SyntaxError: Lỗi cú pháp.
TypeError: Lỗi kiểu dữ liệu.
ReferenceError: Lỗi tham chiếu.
Tuy nhiên trong ứng dụng thưc tế , có những lỗi mang ý nghĩa nghiệp vụ riêng mà các lỗi có sẵn k thể mô tả chính xác 
Ví dụ: Khi đọc thông tin người dùng từ JSON:
<!-- 
const user = JSON.parse('{"age": 25}');

console.log(user.name); // undefined
 -->
JSON trên hoàn toàn hợp lệ về cú pháp, nhưng dữ liệu ngươi dùng lại thiếu name
Đây không phải SyntaxError , mà lỗi dữ liệu  đáp ứng yêu cầu của ứng dung
Chúng ta muốn tạo một loại lỗi riêng:
<!-- ValidationError -->
Ý nghĩa: dữ liệu này không hợp lệ theo quy tắc validation cửa ứng dụng 
1.1.1. So sánh lỗi có sẵn và Custom Error
| Loại lỗi          | Ý nghĩa                                             |
| ----------------- | --------------------------------------------------- |
| `SyntaxError`     | Sai cú pháp                                         |
| `TypeError`       | Thao tác không phù hợp với kiểu dữ liệu             |
| `ReferenceError`  | Tham chiếu biến không tồn tại                       |
| `ValidationError` | Dữ liệu không đáp ứng quy tắc kiểm tra của ứng dụng |
Ví dụ trong dự án thực tế:
Khi đăng ký tài khoản :
Email sai định đạng : ValidationError
Mật khẩu không đúng độ dài : ValidationError
JSON gửi nên sai cú pháp : SyntaxError.

Thay vì phải sủ dụng chung 1 loại lỗi , chúng ta tạo lỗi riêng để nhận diện và xử lý
Ghi nhớ:
Custome error giúp chúng ta mô tả chính xác nghiệp vụ , thay vì chỉ sử dụng những lỗi mặc định của JS


SyntaxError: JSON sai cú pháp.
ValidationError: JSON đúng cú pháp nhưng dữ liệu không đáp ứng yêu cầu.
TypeError: Thao tác không phù hợp với kiểu dữ liệu.
ReferenceError: Sử dụng biến chưa được khai báo.
Ví dụ thực tế: API đăng ký tài khoản nhận được { age: 25 } nhưng yêu cầu phải có email → ValidationError.

1.2. Cấu trúc của Error class
Để tạo custome error , trước tiên chúng ta cần hiểu cấu trúc của class Error có sẵn trong JS
1.2.1. Error class là gì?
Error là 1 built in của JS , dùng để tạo object đại diện cho lỗi
<!-- 
const err = new Error("Something went wrong");

console.log(err.name);    // Error
console.log(err.message); // Something went wrong
console.log(err.stack);   // Stack trace
 -->
Một Error object thường có thuộc tính quan trọng :
| Thuộc tính | Ý nghĩa                                |
| ---------- | -------------------------------------- |
| `name`     | Tên loại lỗi                           |
| `message`  | Nội dung mô tả lỗi                     |
| `stack`    | Thông tin về luồng gọi hàm dẫn đến lỗi |
1.2.2. Kế thừa từ Error
JS cho phép tạo class mới kế thừa từ Error bằng extends
Ví dụ:
<!-- 
class ValidationError extends Error {

}
-->
Ở đây:
- ValidationError là class con
- Error là class cha
- ValidationError kế thừa thuộc tính và hành vi từ Error

1.2.3. Vai trò của super(message)
Chúng ta cần gọi constructor của class bằng cha supr()
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

const err = new ValidationError("Invalid email");

console.log(err.name);    // ValidationError
console.log(err.message); // Invalid email
console.log(err instanceof ValidationError); // true
console.log(err instanceof Error);            // true
 -->
 Phân tích:
 1. constructor(message)
 Nhận nội dung mô tả lỗi từ bên ngoài
 2. super(message)
Gọi constructor của Error , gưi thiết lập thông tin lỗi như messafe và stack trace
3. this.name = "ValidationError"
Đặt tên loại lỗi thành ValidationError thay vì tên mặc định Error.
4. instanceof
Vì   ValidationError kế thừa Error , nên Object được tạo ra thuộc cả 2 loaik 

1.2.4. Ghi nhớ cấu trúc
<!-- 
class CustomError extends Error {
  constructor(message) {
    super(message);
    this.name = "CustomError";
  }
}
 -->
Đây là càu trúc cơ bản để tạo Custome Error trong JS
Lưu ý : Không gọi super() trước khi truy cập this của class con
Bài tâp :
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

const err = new ValidationError("Invalid email");

console.log(err instanceof Error);
console.log(err.name);
console.log(err.message);
 -->
Giải thích:
- err instanceof Error → true: ValidationError kế thừa từ Error.
- err.name → "ValidationError": Được thiết lập bởi this.name.
- err.message → "Invalid email": Được truyền vào super(message).

1.3. Tạo ValidationError kế thừa Error
1.3.1. Xây dựng class ValidationError
Giả sử ứng dụng yêu cầu object user phải có thuộc tính age
Ta tạo class:
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}
 -->
Class này đại diện cho những lỗi được xảy ra khi dữ liệu k đáp ứng yêu cầu validation
1.3.2. Sử dụng ValidationError
Tạo hàm kiểm tra dữ liệu:
<!-- 
function validateUser(user) {
  if (!user.age) {
    throw new ValidationError("No field: age");
  }

  if (!user.name) {
    throw new ValidationError("No field: name");
  }
}
-->
Thử sử dụng:
<!-- 
const user = {
  name: "Martin"
};

validateUser(user);
 -->
Giải thích:
1. user.age không tồn tại nên có giá trị undefined.
2. Điều kiện !user.age là true.
3. throw tạo và ném ra một ValidationError.
4. Chương trình dừng luồng thực thi hiện tại nếu không có nơi xử lý lỗi.
1.3.3. Bắt Custom Error bằng try...catch
<!-- 
try {
  const user = {
    name: "Martin"
  };

  validateUser(user);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log("Validation failed:", err.message);
  } else {
    throw err;
  }
}
 -->
Kết quả: Validation failed: No field: age
Ở đây:
- Nếu là ValidationError: xử lý lỗi validation.
- Nếu là loại lỗi khác : throw err

Đây chính là cách kết hợp try...catch với Custom Error.
Bài kiểm tra tổng hợp :
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

function validateUser(user) {
  if (!user.email) {
    throw new ValidationError("Missing email");
  }
}

try {
  validateUser({});
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(err.name);
    console.log(err.message);
  }
}
 -->
Giải thích:
1. validateUser({}) không có email nên ném ValidationError.
2. err instanceof ValidationError trả về true.
3. err.name là "ValidationError" vì ta đã gán trong constructor.
4. err.message là "Missing email" vì được truyền vào super(message).

Ghi nhớ: super(message) khởi tạo phần Error của class cha , this.name xác định tên lỗi tuỳ chỉnh

1.4. Sử dụng ValidationError
1.4.1. Mục đích
Sau khi tạo ValidationError , ta có thể sử dụng nó để phân biệt lỗi nghiệp vụ (validation) với các lỗi kỹ thuật khác
Ví dụ: Khi đọc dữ liệu JSON từ server, có thể xảy ra hai loại lỗi:
- SyntaxError : JSON k đúng cú pháp
- ValidationError : JSON hợp lệ nhưng thiếu dữ liệu bắt buộc
1.4.2. Ví dụ thực tế
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

function readUser(json) {
  const user = JSON.parse(json);

  if (!user.age) {
    throw new ValidationError("No field: age");
  }

  if (!user.name) {
    throw new ValidationError("No field: name");
  }

  return user;
}

try {
  const user = readUser('{"age": 25}');
  console.log(user);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log("Invalid data:", err.message);
  } else if (err instanceof SyntaxError) {
    console.log("JSON Syntax Error:", err.message);
  } else {
    throw err;
  }
}
-->
Luồng xử lý:
1. JSON.parse() chuyển chuỗi JSON thành Object
2. Nếu JSON sai cú pháp , nó ném SyntaxError
3. Nếu JSON hợp lệ nhưng thiếu age hoặc name , ta chủ động ném ValidationError.
4. catch dùng instanceof để xác định loại lỗi và xử lý tương ứng
5. Lỗi không thuộc 2 loại tên trên đượuc ném lại bằng throw error

1.4.3. Kiểm tra kiến thức
<!-- 
try {
  readUser('{"age": 25}');
} catch (err) {
  if (err instanceof ValidationError) {
    console.log("Validation");
  } else if (err instanceof SyntaxError) {
    console.log("Syntax");
  }
}
 -->
Phân biệt cần nhớ:

| Tình huống                            | Loại lỗi          |
| ------------------------------------- | ----------------- |
| JSON sai cú pháp                      | `SyntaxError`     |
| JSON đúng cú pháp nhưng thiếu dữ liệu | `ValidationError` |

1.5. Xử lý nhiều loại lỗi bằng instanceof
1.5.1. Tại sao cần instanceof?
Trong 1 chương trình , nhiều loại lỗi có thể xuất hiện cùng 1 lúc
Ví dụ khi xử lý dữ liệu người dùng:
- SyntaxError: JSON sai cú pháp
- ValidationError : Dữ liệu thiếu thông tin bắt buộc 
- TypeError : lỗi liên quan đến kiểu dữ liệu hoặc thao tác k hợp lệ
  
Ta cần xác định loại lỗi để xử lý phù hợp :
1.5.2. Sử dụng instanceof
<!--  error instanceof ErrorClass -->
Kết quả:
true : Object là instance của class đó hoặc class kế thừa từ nó
false : không thuộc class đó nhưng trong chuỗi kế thừa
Ví dụ:
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

try {
  throw new ValidationError("Invalid email");
} catch (err) {
  console.log(err instanceof ValidationError); // true
  console.log(err instanceof Error);           // true
  console.log(err instanceof SyntaxError);     // false
}
 -->
Điểm quan trọng: Vì ValidationError kế thừa Error , nên 1 object ValidationError đồng thời cũng là instance của Error
1.5.3. Thứ tự kiểm tra lỗi
Khi xử lý nhiều loại lỗi  nên kiểm tra lỗi cụ thể trước , lỗi tổng quát sau
<!-- 
try {
  readUser(json);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log("Invalid data:", err.message);
  } else if (err instanceof SyntaxError) {
    console.log("Invalid JSON:", err.message);
  } else if (err instanceof Error) {
    console.log("Unexpected error:", err.message);
  } else {
    throw err;
  }
}
-->
Nếu kiểm tra err instanceof Error trước , các lỗi kế thừa từ Error sẽ bị nhánh này bắt hết , khiến nhưngx nhánh cụ thể phía sau 
k được thực thi

2. Further inheritance
2.1. Tại sao cần kế thừa nhiều cấp?
Ở phần trước, chúng ta đã tạo ra ValidationError kế thừa trực tiếp từ Error
Tuy nhiên , trong ứng dụng thực tế , có thể có cần nhiều loại lỗi chung 1 nhóm đặc điểm 
Ví dụ:
- ValidationError: Lỗi dữ liệu không hợp lệ.
- PropertyRequiredError: Lỗi thiếu thuộc tính bắt buộc.
- Các lỗi khác có thể kế thừa từ ValidationError.

Thay vì để tất cả kế thừa trực tiếp từ Error , ta có thể xây dụng chuỗi kế thừa nhiều đa cấp
Sơ đồ kế thừa:
Error => ValidationError => PropertyRequiredError
Điều này giúp:
- Tái sử dung logic xử lý lỗi 
- Gom nhóm các lỗi có liên quan
- Kiểm tra lỗi ở nhiểu cấp bằng instanceof
2.1.1. Ví dụ về kế thừa nhiều cấp
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

class PropertyRequiredError extends ValidationError {
  constructor(property) {
    super(`No property: ${property}`);
    this.name = "PropertyRequiredError";
    this.property = property;
  }
}

const err = new PropertyRequiredError("username");

console.log(err instanceof PropertyRequiredError); // true
console.log(err instanceof ValidationError);       // true
console.log(err instanceof Error);                 // true
 -->
Điểm cần hiểu:
Một PropertyRequiredError đồng thời là:
- PropertyRequiredError
- ValidationError
- Error
Vì vậy , instanceof kiểm tra được toàn bộ chuỗi kế thừa
JavaScript xác định err thuộc toàn bộ chuỗi kế thừa 
Ghi nhớ: instanceof k chỉ kiếm tra class trục tiếp tạo ra object mà còn kiểm tra class cha trong prototype chain
2.2. Tạo PropertyRequiredError.
2.2.1. Mục đích
Trong phần này , chúng ta sẽ tạo 1 custom error chuyên xủ lý trường hợp thiếu thuộc tính bắt buộc 
Thay vì viết:
<!-- throw new ValidationError("No property: username"); -->
Ta có thể tạo một class riêng:
<!-- throw new PropertyRequiredError("username"); -->
Lợi ích:
- Tên lỗi cụ thể , dễ nhận biết
- Có thể truy cập trực tiếp thuộc tính bị thiếu
- Dễ dàng phân biệt bằng instanceof
2.2.2. Triển khai class
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

class PropertyRequiredError extends ValidationError {
  constructor(property) {
    super("No property: " + property);
    this.name = "PropertyRequiredError";
    this.property = property;
  }
}
 -->
Phân tích từng phần:
1. extends ValidationError: Kế thừa từ ValidationError.
2. constructor(property): Nhận tên thuộc tính bị thiếu.
3. super("No property: " + property): gọi constructor của class cha để khởi tạo message
4. this.name : đặt tên lỗi cụ thể 
5. this.property: lưu tên thuộc tính bị thiếu để có thể truy cập sau này

2.2.3. Sử dụng PropertyRequiredError
<!-- 
function readUser(json) {
  const user = JSON.parse(json);

  if (!user.name) {
    throw new PropertyRequiredError("name");
  }

  if (!user.age) {
    throw new PropertyRequiredError("age");
  }

  return user;
}

try {
  const user = readUser('{"age": 25}');
} catch (err) {
  if (err instanceof PropertyRequiredError) {
    console.log("Missing property:", err.property);
    console.log("Error:", err.message);
  } else {
    throw err;
  }
}
 -->
Điểm đáng chú ý: err.property là thuộc tính riêng do chúng ta tự định nghĩa , không phải thuộc tính mặc định của Error
Kiểm tra kiến thức :
<!-- 
const err = new PropertyRequiredError("email");

console.log(err.name);
console.log(err.message);
console.log(err.property);
 -->
err.name: "PropertyRequiredError" — được gán trong constructor.
err.message: "No property: email" — được truyền qua super().
err.property: "email" — thuộc tính riêng được tạo bằng this.property = property.

Điểm cần nhớ:
super() giúp class con tái sử dụng constructor của class cha, còn class con có thể bổ sung thuộc tính và hành vi riêng.

2.3. Bổ sung thông tin riêng cho Custom Error
2.3.1. Mục đích
Ngoài các thuộc tính mặc định của Error :
name : tên loại lỗi
message : nội dung lỗi
stack : thông tin về luồng gọi hàm dẫn đến lỗi
Chúng ta có thể bổ sung các thuộc tính riêng để lưu thêm thông tin cần thiết 
Ví dụ với PropertyRequiredError
<!-- 
class PropertyRequiredError extends ValidationError {
  constructor(property) {
    super("No property: " + property);
    this.name = "PropertyRequiredError";
    this.property = property;
  }
}
 -->
Ở đây:
<!-- this.property = property; -->
Là thuộc tính riêng do chúng ta tự định nghĩa
2.3.2. Truy cập thông tin riêng
<!-- 
try {
  throw new PropertyRequiredError("email");
} catch (err) {
  console.log(err.name);
  console.log(err.message);
  console.log(err.property);
}
 -->
2.3.3. Ví dụ thực tế trong ứng dụng
Giả sử API trả về dữ liệu người dùng:
<!-- 
const user = {
  name: "Martin",
  age: 25
};
 -->
 Ta cần kiểm tra trường email
 <!-- 
 function validateUser(user) {
  if (!user.email) {
    throw new PropertyRequiredError("email");
  }
}
 -->
Khi xử lý lỗi:
<!-- 
try {
  validateUser(user);
} catch (err) {

  } else {
    throw err;

}
 -->
 Trong ứng dung thực tế , thông tin riêng như property , code , statusCode có thể giúp frontend xác định trường cần hiển thị lỗi
 hoặc cách xử lý phù hợp
 2.3.4. Kiểm tra kiến thức
 <!-- 
 class MyError extends Error {
  constructor(message, code) {

const err = new MyError("Request failed", 500);

  -->
2.4. Tạo MyError làm lớp lỗi cơ sở
2.4.1. Tại sao cần MyError?
Khi ứng dụng có nhiều loại tuỳ chỉnh , việc cho từng class kế thừa trực tiếp từ Error có thể khiến code lặp lại 
Ví dụ:
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}

class DatabaseError extends Error {
  constructor(message) {
    super(message);
    this.name = "DatabaseError";
  }
}
 -->
 Cả hai class đều phải viết lại logic khởi tạo message và name 
 Ta có thể tạo class cở sở MyError để dùng chung logic này
 2.4.2. Tạo MyError
 <!-- 
 class MyError extends Error {
  constructor(message) {
    super(message);
    this.name = this.constructor.name;
  }
}
  -->
chú ý : this.name = this.constructor.name;
this.constructor: Constructor thực tế tạo ra object
.name : tên của class đó
Nhờ vậy class con k tự gán this.name nữa
2.4.3. Các class kế thừa MyError
<!-- 
class ValidationError extends MyError {}

class DatabaseError extends MyError {}

class PropertyRequiredError extends ValidationError {

}
-->
Khi tạo object

const err1 = new ValidationError("Invalid data");

console.log(err1.name); // ValidationError
console.log(err2.name); // DatabaseError
console.log(err3.name); // PropertyRequiredError
 -->
Ta không cần viết lại this.name trong từng class con
2.4.4. Sơ đồ kế thừa
Error
  │
  └── MyError
        │
        ├── ValidationError
        │     │

        └── DatabaseError
2.4.5. Kiểm tra kiến thức
<!-- 
class MyError extends Error {

class ValidationError extends MyError {}

class PropertyRequiredError extends ValidationError {}

const err = new PropertyRequiredError("Missing email");

console.log(err.name);

console.log(err instanceof Error);
 -->
 1. err.name → "PropertyRequiredError" vì this.constructor.name lấy tên class thực tế tạo ra object.
 2. err instanceof ValidationError → true vì PropertyRequiredError kế thừa ValidationError.
 3. err instanceof MyError → true vì chuỗi kế thừa đi qua MyError.
 4. err instanceof Error → true vì MyError kế thừa Error.
this.constructor.name
giúp class cha tự động xác định tên class con , tránh phải gán this.name thủ công cho từng class

- Kế thừa Custom Error nhiều cấp.
- Tạo PropertyRequiredError.
- Bổ sung thuộc tính riêng như property, code.
- Tạo MyError làm lớp lỗi cơ sở.
- Sử dụng this.constructor.name.

3. Wrapping exceptions
3.1. Vấn đề khi xử lý nhiều loại lỗi
Trong ứng dụng thực tế , 1 hàm có thể gọi nhiều hàm khác nhau và mỗi hàm có thể phát sinh 1 lỗi riêng
<!-- 
function readUser() {
  // Đọc dữ liệu người dùng từ file
}

function loadConfig() {
  // Đọc cấu hình từ file
}

function startApp() {
  readUser();
  loadConfig();
}
 -->
 Giả sử:
- readUser() có thể phát sinh SyntaxError khi JSON sai cú pháp
- loadConfig() có thể phát sinh SyntaxError khi file cấu hình k hợp lệ
- Các hàm khác cũng có thể phát sinh nhiều loại lỗi khác nhau

Khi xử lý ở startApp() , chúng ta phải biết lỗi đến từ đâu và thuộc loại nào
3.1.1. Vấn đề khi bắt lỗi trực tiếp
<!-- 
try {
  readUser();
} catch (err) {
  if (err instanceof SyntaxError) {
    console.log("JSON parsing error");
  } else {
    throw err;
  }
}
-->
Cách này có 1 số hạn chế : SyntaxError chỉ cho biết lõi cú pháp , nhưng k cho biết nó xảy ra trong quá trình đọc user hay config
Nều nhiều tâng xử lý cùng sử dung loại lỗi giống nhau , việc phân biệt nguồn gốc lỗi sẽ khó khăn hơn
3.1.2. Ý tưởng giải quyết
Ta có thể:
1. Bắt lỗi thấp tại nơi phát sinh
2. Tạo một lỗi cấp cao hơn đại diện cho nghiệp vụ đang thực hiện
3. Lưu lỗi ban đầu bên trong lỗi mới
4. Ném lỗi mới lên tầng xử lý bên ngoài

Đây chính là ý tưởng của Wrapping exceptions.
Ghi nhớ: loại lỗi chỉ cho biết lỗi gì xảy ra , còn wrapping exceptions giúp bổ sung thông tin về lỗi xảy ra trong ngữ cảnh nào

3.2. Wrapping exceptions là gì?
3.2.1. Khái niệm
Wrapping exceptions (bọc ngoại lệ) là kỹ thuật bắt 1 lỗi cấp thấp , sau đó tạo 1 lỗi mới ở cấp cao hơn dể bổ sung ngữ cảnh , đông thời 
giữ lại lỗi ban đầu
Ví dụ:
- Lỗi cấp thấp: SyntaxError – JSON sai cú pháp.
- Lỗi cấp cao: ReadError - không thể đọc dữ liệu người dùng

Thay vì SyntaxError truyền trực tiếp lên bên ngoài , ta bọc nó trong ReadError
3.2.2. Ví dụ đơn giản
Không wrapping:
<!-- 
function readUser(json) {
  return JSON.parse(json);
}

try {
  readUser("{ invalid json }");
} catch (err) {
  console.log(err.name); // SyntaxError
}
 -->
Có wrapping:
<!-- 
class ReadError extends Error {
  constructor(message, cause) {
    super(message);
    this.name = "ReadError";
    this.cause = cause;
  }
}

function readUser(json) {
  try {
    return JSON.parse(json);
  } catch (err) {
    throw new ReadError("Cannot read user data", err);
  }
}

try {
  readUser("{ invalid json }");
} catch (err) {
  console.log(err.name);        // ReadError
  console.log(err.message);     // Cannot read user data
  console.log(err.cause.name);  // SyntaxError
}
 -->
3.2.3. Vai trò của cause
Trong ví dụ trên:
<!-- this.cause = cause; -->
cause lưu lại lỗi ban đầu.
| Thuộc tính    | Ý nghĩa                        |
| ------------- | ------------------------------ |
| `err.name`    | Loại lỗi mới                   |
| `err.message` | Thông báo lỗi mới              |
| `err.cause`   | Lỗi ban đầu được bọc bên trong |
Nhờ vậy , tầng bên ngoài chỉ cần xử lý ReadError , nhưng vẫn có thể truy cập lỗi gốc thông qua err.cause
Lưu ý: cause là thuộc tính được JS hỗ trợ từ năm 2022
3.2.4. Kiểm tra kiến thức
<!-- 
const originalError = new SyntaxError("Invalid JSON");

const wrappedError = new Error("Cannot read data", {
  cause: originalError
});

console.log(wrappedError.name);
console.log(wrappedError.message);
console.log(wrappedError.cause.name);
 -->
Error
Cannot read data
SyntaxError
Ở đây chúng ta tạo một object Error mới và truyền lỗi ban đầu vào tùy chọn cause.
- wrappedError.name → "Error": Vì object được tạo bằng new Error().
- wrappedError.message → "Cannot read data": Message của lỗi mới.
- wrappedError.cause.name → "SyntaxError": Tên loại lỗi ban đầu.
Điểm cần phân biệt:
cause k thể thay thế lỗi cũ mà lưu lỗi cũ bên trong lỗi mới
wrappedError
  ├── name: "Error"
  ├── message: "Cannot read data"
  └── cause
        ├── name: "SyntaxError"
        └── message: "Invalid JSON"

3.3. Tạo ReadError và thuộc tính cause
3.3.1. Tạo class ReadError
Chúng ta đã hiểu wrapping exceptions . Bây giờ sẽ xây dụng Custom Error cụ thể tên ReadError
<!-- 
class ReadError extends Error {
  constructor(message, cause) {
    super(message);
    this.name = "ReadError";
    this.cause = cause;
  }
}
-->
| Thành phần      | Ý nghĩa                  |
| --------------- | ------------------------ |
| `extends Error` | Kế thừa Error            |
| `message`       | Thông báo lỗi mới        |
| `cause`         | Lỗi ban đầu được bọc     |
| `this.name`     | Đặt tên lỗi là ReadError |

3.3.2. Sử dụng ReadError
Giả sử chúng ta đọc dữ liệu người dùng từ JSON:
<!-- 
function readUser(json) {
  try {
    return JSON.parse(json);
  } catch (err) {
    throw new ReadError("Cannot read user data", err);
  }
}
-->
Khi JSON không hợp lệ:
1. JSON.parse() ném SyntaxError.
2. catch bắt được lỗi này
3. Tạo ReadError mới , truyền lỗi ban đầu vào cause
4. throw đưa ReadError ra ngoài.

3.4. Chuyển lỗi cấp thấp thành lỗi cấp cao.
3.4.1. Mục đích
Trong ứng dụng có nhiều tầng ử lý , mỗi tầng có thể cần 1 cách biểu diễn lỗi khác nhau
Ví dụ khi đọc dữ liệu người dùng:
| Tầng               | Loại lỗi           | Ý nghĩa                          |
| ------------------ | ------------------ | -------------------------------- |
| JavaScript parsing | `SyntaxError`      | JSON sai cú pháp                 |
| Data reading       | `ReadError`        | Không thể đọc dữ liệu người dùng |
| Application        | `ApplicationError` | Lỗi ở tầng ứng dụng              |
Thay vì để lỗi kỹ thuật ở cấp thấp truyền toàn bộ nên ứng dụng , ta chuyển chúng thành lỗi phù hợp với tưng tầng
3.4.2. Ví dụ thực tế
<!-- 
class ReadError extends Error {
  constructor(message, cause) {
    super(message, { cause });
    this.name = "ReadError";
  }
}

function readUser(json) {
  try {
    return JSON.parse(json);
  } catch (err) {
    throw new ReadError("Cannot read user data", err);
  }
}
 -->
Ở đây:
- JSON.parse() phát sinh SyntaxError.
- readUser() bắt lỗi và tạo ReadError.
- - cause lưu lại SyntaxError ban đầu.
3.4.3. Xử lý ở tầng bên ngoài
<!-- 
try {
  const user = readUser("{ invalid json }");
} catch (err) {
  if (err instanceof ReadError) {
    console.log("User data error:", err.message);
    console.log("Original error:", err.cause);
  } else {
    throw err;
  }
}
-->
Tầng bên ngoài chỉ quan tâm đến RedError , không cần chi tiết bên trong hàm readUser() đã sử dungj JSON.parse() như thế nào
Điểm quan trọng: wrapping exception giúp tách biệt trách nhiệm giữa các tầng , đồng thời k làm mất thông tin gốc
3.5. Xử lý lỗi sau khi wrapping
3.5.1. Xử lý lỗi ở tầng bên ngoài
Sau khi wrapping , tầng bên ngoài thường chỉ quan tâm đến loại lỗi cấp cao
Ví dụ:
<!-- 
class ReadError extends Error {
  constructor(message, cause) {
    super(message, { cause });
    this.name = "ReadError";
  }
}

function readUser(json) {
  try {
    return JSON.parse(json);
  } catch (err) {
    throw new ReadError("Cannot read user data", err);
  }
}

try {
  readUser("{ invalid json }");
} catch (err) {
  if (err instanceof ReadError) {
    console.log("Read failed:", err.message);
    console.log("Original cause:", err.cause.name);
  } else {
    throw err;
  }
}
 -->
Kết quả :
Read failed: Cannot read user data
Original cause: SyntaxError

3.5.2. Khi nào cần truy cập cause?
Có hai tình huống:
Trường hợp 1: Chỉ cần xử lý lỗi cấp cao
<!-- 
if (err instanceof ReadError) {
  showNotification("Không thể đọc dữ liệu");
}
 -->
Frontend chỉ cẩn hiển thị thông báo phù hợp , k nhất thiết phải biết lỗi kĩ thuật bên trong
Trường hợp 2: Cần kiểm tra lỗi gốc để debug
<!-- 
if (err instanceof ReadError) {
  console.error("Read error:", err.message);
  console.error("Original error:", err.cause);
}
 -->
Lúc này cause giúp tìm nguyên nhân gây lỗi thực sự 
3.5.3. Phân biệt throw err và wrapping
| Cách xử lý                      | Ý nghĩa                                 |
| ------------------------------- | --------------------------------------- |
| `throw err`                     | Ném lại chính lỗi ban đầu               |
| `throw new ReadError(..., err)` | Tạo lỗi mới và lưu lỗi cũ trong `cause` |
<!-- 
catch (err) {
  throw err;
}
 -->
 k tạo lỗi mới
Trong khi:
<!-- 
catch (err) {
  throw new ReadError("Cannot read data", err);
}
 -->
tạo lỗi mới nhưng vẫn giữ thông tin ban đầu
3.5.4. Kiểm tra kiến thức
<!-- 
try {
  readUser("{ invalid json }");
} catch (err) {
  if (err instanceof ReadError) {
    console.log(err.name);
    console.log(err.cause.name);
  }
}
 -->
 Giải thích:
- err.name → ReadError: lỗi mới được tạo ra khi wrapping.
- err.cause.name → SyntaxError: lỗi gốc được lưu trong cause.

4. Summary
4.1. Tổng kết Custom Errors
1. Extending Error

Tạo lỗi tùy chỉnh bằng cách kế thừa Error.
<!-- 
class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
  }
}
 -->
 Mục đích: Phân biệt lỗi nghiệp vụ với lỗi JavaScript có sẵn.
2. Further inheritance
Cho phép Custom Error kế thừa nhiều cấp.
<!-- 
class MyError extends Error {
  constructor(message) {
    super(message);
    this.name = this.constructor.name;
  }
}

class ValidationError extends MyError {}

class PropertyRequiredError extends ValidationError {
  constructor(property) {
    super(`No property: ${property}`);
    this.property = property;
  }
}
 -->
Mục đích: Tái sử dụng logic, bổ sung thông tin riêng và tổ chức các nhóm lỗi.
3. Wrapping exceptions
Bọc lỗi cấp thấp bằng lỗi cấp cao hơn, giữ lỗi gốc trong cause.
<!-- 
class ReadError extends Error {
  constructor(message, cause) {
    super(message, { cause });
    this.name = "ReadError";
  }
}
 -->
4.1.1. Bảng ghi nhớ
| Kiến thức                       | Ý nghĩa                            |
| ------------------------------- | ---------------------------------- |
| `extends Error`                 | Tạo Custom Error                   |
| `super(message)`                | Khởi tạo phần Error của class cha  |
| `this.name`                     | Đặt tên lỗi                        |
| `this.constructor.name`         | Lấy tên class thực tế              |
| `instanceof`                    | Kiểm tra loại lỗi và chuỗi kế thừa |
| `this.property`                 | Bổ sung thông tin riêng            |
| `cause`                         | Lưu lỗi ban đầu                    |
| `throw err`                     | Ném lại lỗi cũ                     |
| `throw new ReadError(..., err)` | Tạo lỗi mới và bọc lỗi cũ          |
4.1.2. Kiến thức cần vận dụng trong ReactJS
Khi làm việc với API, bạn có thể gặp các nhóm lỗi:
- ValidationError: Dữ liệu không hợp lệ.
- NetworkError: Không thể kết nối server.
- AuthenticationError: Người dùng chưa xác thực.
- ApiError: Lỗi trả về từ API.
Có thể xây dựng hệ thống CustomError để phân loại vả xử lỷ lỗi nhất quan thay vì chỉ dựa vào console.error().
